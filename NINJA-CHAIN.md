# NINJA CHAIN — continuous systems showcase

A single scripted run through the Portal Test Chamber that shows every gameplay
system back to back, with **no cuts and no teleports for the camera**.  This
file is the requirements + implementation reference; the general test workflow
is in `TESTING.md`.

## Requirements (from the brief)

- [x] One continuous run in the test chamber: wall-run → grapple → jetpack →
      portals → ball blaster → ground pound → punch/kick of Box3D cubes.
- [x] Collect a star (checkpoints along the route count; the N6 finale star is
      the completion condition).  Two stars: N4 after the grapple, N6 after the
      ceiling-portal drop.
- [x] No camera cuts: one follow camera for the whole run (`cmode=3`, no
      freelook pin, one continuous run).
- [x] Starts in the **custom camera**.
- [x] Tapping **R** in the custom camera springs it back behind Mario with a
      racing-game lag (critically damped, not a snap); ignored while the grapple
      rope is attached.
- [x] Chamber rearranged into a ninja-warrior course (collision + visuals).
- [x] Bonus: a goomba is dispatched through a portal pair — a portal on the
      ceiling and one in front of the goomba — and loops "like a lemming".
      Crossings are counted in the dump (`chain=...,<crossings>,...`).

| --- | --- | --- | --- | --- |
| spawn | start / box3d floor | -450 | -1000 | 0 |
| L1 | jetpack launch pad | -1100 … -600 | -1600 … -1400 | 450 |
| N1 | wall-run wall (west face x=-360) | -360 … -300 | -2350 … -1400 | 700 |
| N2 | wall-run catch | -950 … -360 | -2700 … -2350 | 330 |
| N3 | grapple anchor pillar (anchor at y≈800) | -150 … -90 | -2850 … -2790 | 950 |
| N4 | grapple catch / star 1 | -200 … 1000 | -3200 … -2600 | 200 |
| N5 | jetpack target | 1200 … 2100 | -3150 … -2600 | 900 |
| N7 | player portal tower (portal at x=1896, y≈1050) | 1900 … 2100 | -3000 … -2800 | 1700 |
| N6 | ceiling-portal landing / star 2 | -900 … -300 | -3200 … -2700 | 1500 |
| N8 | goomba gate pillar (portal at x≈-454, y≈1620) | -450 … -390 | -3100 … -2900 | 2100 |

Route in order:

1. **Box3D opening** on the spawn floor: ball blaster knocks a 3-cube tower,
   then a punch, a jump kick and a ground pound clear the single cubes placed
   at z = -1270 / -1390 / -1510.
2. **Jetpack #1** up to L1 (the first star is not here; L1 only sets the height).
3. **Wall-run** east off L1 into N1, then south for the 52-tick run.
4. **Grapple** from N2 to the N3 anchor and swing/release onto N4.
5. **Star 1** on N4 at (300, 420, -2950).
6. **Jetpack #2** east from N4 to N5.
7. **Portals**: blue on the N7 west face, orange on the room ceiling above N6;
   run into blue, drop out of the ceiling onto N6.
8. **Star 2** on N6 at (-750, 1620, -3100).
9. **Goomba lemming**: re-shoot the blue portal onto the N8 gate, keep the
   ceiling portal, spawn a goomba that walks into the gate and falls out of the
   ceiling in a loop (crossings counted in the dump).

## Driver (`app/jni/src/src/game/ptc.c`)

`ptc_chain_*` is a tick-based state machine.  It advances on **world state**
(action, grounded, position, teleport count, star flags), never on a camera cut.
Mario's input comes from `ptc_mario_input_override()` → `ptc_chain_input()`.

| phase | goal |
| --- | --- |
| `CH_BOX_BALL/WALK/PUNCH/WALK/KICK/WALK/SLAM` | Box3D opening |
| `CH_JET_L1` | jetpack to the wall-run height |
| `CH_RUN_WALL` / `CH_WALLRUN` / `CH_WALL_LAND` | wall-run + catch |
| `CH_GRAPPLE_*` | aim hint, attach, swing, release |
| `CH_STAR1` | walk over the N4 star |
| `CH_JET_N5` | jetpack to N5 |
| `CH_PORTAL_RUN/FALL` | portal to N6 |
| `CH_STAR2` | walk over the N6 star |
| `CH_GOOMBA_SETUP/LOOP` | lemming loop forever |

Run it:

```bash
B="am broadcast -n com.vdavid003.sm64port/.DebugReceiver -a com.vdavid003.sm64port.CMD"
adb shell "$B --es cmd level --ei n 38"
adb shell "$B --es cmd ptc --es action chain"          # full run from the start
```

From the tablet UI: **ENH → PORTAL → RUN NINJA CHAIN**.  It loads level 38,
waits 2.5 s, then starts `chain`; **STOP NINJA CHAIN** calls `chainoff`.  The
PORTAL page is laid out in three columns (ninja/tests, live scene, knobs +
annexes) so it needs minimal scrolling.

Per-section starts for tuning (each resets the chain and places Mario):

```bash
adb shell "$B --es cmd ptc --es action chainbox"       # box3d opening
adb shell "$B --es cmd ptc --es action chainwall"      # wall-run
adb shell "$B --es cmd ptc --es action chaingrapple"   # grapple
adb shell "$B --es cmd ptc --es action chainjet"       # jetpack + portal
adb shell "$B --es cmd ptc --es action chainportal"    # portal + N6
adb shell "$B --es cmd ptc --es action chaingoomba"    # lemming loop
adb shell "$B --es cmd ptc --es action chainoff"
```

Dump tokens added for the chain:

```
chain=<phase>,<timer>,<flags hex>,<goomba crossings>,<cubes near start>
```

`flags` bits: 1 ball, 2 punch, 4 kick, 8 slam, 16 jetpack, 32 wallrun,
64 grapple, 128 portal, 256 star1, 512 star2, 1024 goomba.

## Fast-forward runner

`cmd runticks --ei n N` runs N 30 Hz simulation ticks back to back on the game
thread (no present, no audio), then renders one normal frame.  It is the
fastest way to iterate on chain logic: 200 ticks (~6.7 s of gameplay) complete
in a fraction of a second, with the same physics, scripted input, camera and
grapple aiming as a real run.

```bash
B="am broadcast -n com.vdavid003.sm64port/.DebugReceiver -a com.vdavid003.sm64port.CMD"
adb shell "$B --es cmd level --ei n 38"
adb shell "$B --es cmd ptc --es action chainbox"   # section setup, unchanged
sleep 1
adb shell "$B --es cmd runticks --ei n 200"
sleep 1
adb shell "$B --es cmd trace"                      # SM64Leia logcat
```

`cmd trace` logs the buffer one line per record; every 15 ticks plus the final
state:

```
t=120 ph=12 fl=0x020 act=0x0300089A pos=-408,509,-1536 st=10 gx=0 cm=3
```

Fields: `t` global timer, `ph` chain phase, `fl` flags, `act` Mario action,
`pos` position, `st` star0/star1, `gx` goomba crossings, `cm` camera mode.
Footers carry the device timing: `# done ran=200 sim_ms=... real30_ms=...`,
`# speedup_x100=...`; `PTC runticks done n=.. ms=..` is also logged when the
batch finishes.

Harness mode (same assertions as the dump path, plus timing and one
post-batch screenshot):

```bash
scripts/ninja-chain-test.py --fast --section chainwall --ticks 200
scripts/ninja-chain-test.py --fast --section chainbox --ticks 200 --install
```

Caveats: the batch skips rendering, so portal FBO/decal visuals and
screenshots still need normal mode (the run renders one frame at the end).
Audio is not buffered during the batch, the trace keeps only its tail, and
requests are clamped to 2400 ticks.  `runticks` leaves `gfx_test_uncapped`
off.  Recommended loop: `--fast` for flags/stars/crossings, then the default
real-time harness for screenshots and the final visual pass.

## Camera (custom, always)

- The chain **forces the custom camera** (`custom_camera_apply_mode(3)`) in
  `ptc_chain_setup()`, sets distance 700 / height 110, clears any freelook pin
  and re-inits the orbit.  Every section start (`chainwall`, `chaingrapple`, …)
  goes through the same setup, so a stale vanilla/POV camera can never leak in.
- The green note is prefixed `CUSTOM CAM |` and the dump should read
  `cmode=3` (added with the chain dump token) so a screenshot/log proves the
  camera mode.
- Scripted pans use `custom_camera_set_focus_hint()`: the camera *position*
  keeps following Mario, only the look-at point eases towards the grapple
  anchor / ball target / goomba.  No cuts.
- **R shoulder** in the custom camera starts a critically damped yaw spring
  towards "behind Mario" (racing-game lag/overshoot).  R is ignored while the
  grapple rope is attached (it is also the retract button).
- **WALL NOCLIP** is on by default for the custom camera: it skips the collision
  pull-in, lets the camera pass through a room wall and hides that wall (PTC
  walls only).  Toggle with `cmd set --ei k 52 --ei v 0/1` or the CAMERA tab.
  `ptc camwall` demonstrates it: on = camera outside the west wall with the wall
  gone; off = pulled-in close-up.  Camera distance/FOV are also tunable
  (`k 46` / `k 20`) for framing.

## Green test note

The Android debug panel has a green line that says what is being tested and the
desired outcome.  Scripted phases update it automatically; adb can override it:

```bash
adb shell "$B --es cmd note --es text 'NINJA 3/8: expect a 52-tick wall-run'"
```

The chain note table is `ptc_chain_note()`; the native channel is
`--es cmd note --es text ...` → `nativeSetDebugNote()` → the panel's green
`debugView` line.

## Faster iteration (host-side Python driver)

Device round trips dominate: install ~5–10 s, level load ~8 s, then the run in
real time.  Keep the *simulation* in the real engine; use Python only as the
harness / planner.

1. **In-engine fast-forward (done).**  `cmd runticks --ei n 900` queues N
   ticks; `produce_one_frame()` sets `gfx_test_uncapped`, runs N
   `game_loop_one_iteration()` steps, restores it and renders one normal
   frame.  `cmd trace` returns the compact per-15-tick trace (phase, pos,
   action, flags, stars, crossings, cam mode) plus device timing; see
   "Fast-forward runner" above.  Physics, input, camera and grapple aiming
   still update; only rendering is skipped, so visuals/screenshots still need
   normal mode.
2. **`scripts/ninja-chain-test.py` (host).**  One device-lock session: load
   level 38, run a section or the full `chain`, poll `cmd dump`, assert
   `chain` flags / `star=` / `goomba crossings`, save 2–4 checkpoint PNGs and
   print a pass/fail table.  This removes manual adb loops and makes the
   acceptance criteria machine-checkable.
3. **Native Linux build of the same C engine (long term).**  Add a host target
   (SDL2 + OpenGL under Xvfb or OSMesa) with `--scenario` and JSONL/PNG output.
   Iterations drop to ~1 s and no install/unlock is needed; keep Android as the
   final fidelity validation.

Do **not** reimplement Mario's movement in Python: the wall-run speed/wall
probe, grapple rope constraint and Box3D impulses are exactly where a model
would drift from the engine.  Python may *propose* jump positions or parse
traces, but every candidate is validated in the engine.

## Verification checklist

1. `chainbox`: cubes scattered, flags gain 1/2/4/8, no crash.
2. `chainwall`: `action=0x0300089A` (ACT_WALLRUN) seen, flag 32, lands on N2.
3. `chaingrapple`: `movekit_state() & 8`, flag 64, lands on N4.
4. `chainjet`: flag 16 + 128, `tele` increments, Mario ends on N6.
5. `chainportal`: teleport + drop; `pov`-style screenshot of the fall if needed.
   Confirm the dump shows `cmode=3` (custom camera) for the whole run.
6. `chaingoomba`: `goomba crossings` increases every few seconds.
7. Full `chain`: all flags set, both stars collected, run stays on one camera.
8. Screenshots are mono (flat 2D) because the Leia weave makes stills unreadable.

Known caveat: the driver is deterministic but physically tuned; if a phase
times out it advances without the flag, which the dump makes obvious.  Re-tune
the phase timings/positions rather than adding teleports, to keep the run
continuous.
