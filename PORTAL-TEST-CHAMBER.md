# Portal Test Chamber

A deterministic graybox level used by the portal traversal regression test.
It reuses the last unused level slot (`LEVEL_UNKNOWN_38`, id **38**) so the
game's level-count-sized tables do not change.

The level is generated by `scripts/gen-ptc-level.py`; the generated C lives in
`app/jni/src/levels/ptc/`. Re-run the generator after editing the geometry
constants, then rebuild:

```sh
python3 scripts/gen-ptc-level.py
```

## World-space layout

All values are N64 units. Mario is 160 units tall and his feet are at `pos.y`.

| Element | X range | Z range | Top / centre Y |
|---|---|---|---|
| Room floor | -1200 … 1200 | -1800 … 1200 | 0 |
| Room ceiling | -1200 … 1200 | -1800 … 1200 | 1400 |
| P1 normal jump | -1050 … -750 | -650 … -350 | **180** |
| P2 stronger jump | 750 … 1050 | -650 … -350 | **360** |
| P3 near max jump | -1050 … -750 | 150 … 450 | **560** |
| P4 ledge grab | 750 … 1050 | 150 … 450 | **680** |
| P5 portal platform | -600 … 600 | 600 … 1200 | **800** |
| P6 entry wall (portal A) | -750 … -450 | -400 … -300 | 200 |

Walls are covered by a 1-unit × 1-unit checkerboard (an 8×8 texel texture with
4×4 checks and 4 texels per world unit, point filtered). The room is lit with
fixed vertex colours only; no external skybox or time-of-day state is used.

### Portal targets and test objects

| Object | World position | Notes |
|---|---|---|
| Mario start | `(-600, 0, -950)` | facing `0` (+Z), towards the near portal wall |
| Entry portal (blue, P1) | hitscan target `(-600, 100, -400)` | P6 `-Z` face, normal `-Z`; decal lands at `z = -401.5` |
| Exit portal (orange, P2) | hitscan target `(0, 900, 1199)` | back wall behind P5, normal `-Z`; decal lands at `z = 1198.5` |
| Debug star | `(180, 870, 900)` | on P5, model `MODEL_STAR`; offset so it is visible beside Mario on exit |

The exit portal is 100 units above the P5 surface so Mario's centre of mass
(80 units above his feet) emerges at `y = 880`, leaving his feet exactly on the
800-unit platform. The entry portal centre is at `y = 100`, so entering with
Mario's centre at `y = 80` produces the same relative offset. The exit push is
90 units, outside the 70-unit portal-entry trigger; this prevents an immediate
reverse teleport while Mario stands still after arriving.

The star uses a custom debug behaviour with `INTERACT_COIN` (value 0), not
`INTERACT_STAR_OR_KEY`. It therefore cannot call
`save_file_collect_star_or_key()`: collecting it never changes the save file or
`gMarioState->numStars`. Its state is exposed as `star=` in the headless dump.

## Calibration

Platform heights are chosen from the movement limits in the decomp:

- single jump: `42 + 0.25 * forwardVel` initial upward speed, gravity `4`
- double jump: `52 + 0.25 * forwardVel`, forward speed retained
- triple jump: `69` initial upward speed
- ledge grab: a ledge may be at most **100 units** above Mario's feet when the
  wall is touched (`check_ledge_grab` in `mario_step.c`)

Measured on the device with `CALIBRATE JUMPS` (full forward run, A held):

| Jump | Measured peak |
|---|---|
| single | 338 |
| double | 480 |
| triple | 630 |
| ledge-grab reach (triple peak + engine's 100-unit ledge window) | 730 |

The in-game `CALIBRATE JUMPS` debug button (or `cmd ptc` with action
`calibrate`) repeats this measurement and prints `cal=single,double,triple
ledge_reach=…` in the PTC dump. The chosen platform heights sit inside the
measured bands with margin:

- 180: single jump, comfortably reachable
- 360: requires a double jump (single jump is not enough)
- 560: requires a triple jump near its apex
- 680: requires a triple jump plus a ledge grab (measured reach 730)
- 800: unreachable by jump/ledge-grab from the floor

If the measured values on a new build differ, update
`scripts/gen-ptc-level.py`, regenerate, and re-run the traversal test.

## Headless controls

Set `B` as in the main README, then:

```sh
adb shell $B --es cmd level --ei n 38
adb shell $B --es cmd ptc --es action reset      # level, Mario, portals, star
adb shell $B --es cmd ptc --es action run        # full automated traversal
adb shell $B --es cmd ptc --es action calibrate  # measure single/double/triple
adb shell $B --es cmd ptc --es action place      # place the two test portals
adb shell $B --es cmd ptc --es action stop
adb shell $B --es cmd uncapped --ei v 1          # debug-only test execution
adb shell $B --es cmd hz --ei v 60               # physical panel 60/120 Hz mode
adb shell $B --es cmd dump                       # includes one "PTC ..." line
```

When adb is reached through a host-forwarded server (as on the shared test
machine), export `ADB_SERVER_SOCKET=tcp:10.0.2.2:5037` before running the
scripts.

`PTC ...` contains the current phase, portal positions/orientations, teleport
source/destination, Mario position/velocity/action/floor, collision flags,
ledge-grab state, star state, real/save star counts, and the calibration
values. The phase values are:

| Phase | Meaning |
|---|---|
| 0 | idle / reset |
| 1 | portals being placed (visible setup pause) |
| 2 | Mario walking into the blue portal |
| 3 | teleport / arriving on P5 |
| 4 | walking to the debug star |
| 5 | PASS |
| 6 | FAIL (see `reason=`) |
| 7 | calibration |

## Automated regression test

```sh
scripts/agent-lock.sh device --reason "portal smoke test" -- \
    scripts/test-portal-chamber.sh
```

The script:

1. starts the app and warps to level 38;
2. resets the level, Mario, portals and debug star;
3. records the real and save-file star counts;
4. runs the traversal (deterministic hitscan portals, scripted walking);
5. captures screenshots at load/reset/portal-placement/walk/teleport/star;
6. asserts both placements, `src=0`, `dst=1`, `onplat=1`, `star=1`, and that
   both star counts are unchanged;
7. runs the same traversal with **UNCAPPED TEST SIM** and compares the final
   gameplay state (`mario`, `vel`, `action`, teleport, star, platform, portal
   and star-count fields) against the capped run.

The level's 3D labels (`P1`…`P5`, `A`, `B`) are baked into the level display
lists, so they remain visible in recordings and do not depend on the 2D HUD
pass.

Artifacts (screenshots, `final-state.txt`, `uncapped-final-state.txt`, and
`failure.txt`/`failure-logcat.txt` on failure) are written to:

```
test-artifacts/portal-chamber/<timestamp>/
```

A successful run ends with `PASS`, phase 5, and:
`portals=2 shotA=1 shotB=1 tele>=1 src=0 dst=1 onplat=1 star=1`.

## Demonstration video

```sh
scripts/agent-lock.sh device --reason "record portal demo" -- \
    scripts/record-portal-chamber.sh
```

The recorder explicitly sets render FPS mode 1 (60 FPS rendering), disables
the uncapped test option, and records the normal 30 Hz simulation. The MP4 is
saved as:

```
test-artifacts/portal-chamber/portal-test-chamber-traversal-60fps-<timestamp>.mp4
test-artifacts/portal-chamber/portal-test-chamber-traversal-60fps.mp4   # stable copy
```

The recorder switches the physical panel to its 60 Hz display mode with the
debug `cmd hz --ei v 60` command, then verifies the delivered file with
`scripts/mp4-fps.py` (no ffmpeg required). A successful recording reports
`avg_fps` within 59–61 and writes `last-video-info.txt` next to the video.


## Momentum-stacking smoke test

The second test uses the same room and a separate arena built from P7/P9 and a
45-degree launch ramp:

| Element | X range | Z range | Top / surface |
|---|---|---|---|
| P7 high drop platform | -300 … 300 | -1500 … -1100 | **1100** |
| 45-degree launch ramp | -250 … 250 | -850 … -550 | **800 at z=-850 → 500 at z=-550** |
| P9 momentum target | -300 … 300 | 150 … 560 | **950** |
| Momentum star | — | at `(0, 1000, 480)` | above P9, at the landing point |

The test shots are deterministic:

- Floor portal A: target `(0, 0, -1042)`, normal `+Y`.  The portal sits on the
  measured vertical drop line: walking off P7 triggers a short ledge-grab/wall
  response that shifts Mario about 58 units past the edge before he falls.
- Angled portal B: target `(0, 650, -700)`, normal `(0, 0.7071, 0.7071)`.

Mario walks off P7, drops vertically through the floor portal, and exits the
ramp portal with the transformed falling momentum (up and +Z). The smoke test
asserts:

- entry and exit speeds both exceed the momentum threshold (>= 55 units/tick);
- the source/destination portal pair is `0 → 1`;
- Mario reaches P9;
- the second debug star is collected;
- the real/save star counts remain unchanged.

While airborne after the exit, the test forces the **cannon flight body pose**
(`MARIO_ANIM_AIRBORNE_ON_STOMACH`, with the same pitch expression used by
`ACT_SHOT_FROM_CANNON`). This is visual-only: the actual momentum and physics
remain the normal portal-launch trajectory.

```sh
scripts/agent-lock.sh device --reason "momentum smoke test" -- \
    scripts/test-portal-momentum.sh

scripts/agent-lock.sh device --reason "record momentum demo" -- \
    scripts/record-portal-momentum.sh
```

Artifacts go to `test-artifacts/portal-chamber/momentum-<timestamp>/`; the
video is `test-artifacts/portal-chamber/portal-momentum-stacking-60fps-<timestamp>.mp4`.

## Uncapped test execution

`UNCAPPED TEST SIM` (ENH tab) or `cmd uncapped --ei v 1` removes only the
display pacing: each loop iteration still advances exactly one fixed 30 Hz
simulation tick, and all movement/physics/collision rules are untouched. The
GL pass and audio submission are skipped while it is enabled, so the screen
keeps the last rendered frame. It is off by default, and the video recorder
turns it off explicitly. The regression script runs the same scenario both
ways and compares the resulting gameplay state.
